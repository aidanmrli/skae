# Problem Formulation: What Is Literally True in the Code

## The specific statement under review

The paper-style statement

> `x_t = x(tΔt)`

is an idealized continuous-time notation. It is not literally how the training data are represented or generated in this codebase.

## Code-faithful statement

What is literally true in the code is closer to:

```tex
x_{t+1} = F_{\Delta t}(x_t),
```

where `F_{\Delta t}` is the one-step simulator used by the environment.

For most built-in environments, `F_{\Delta t}` is a single RK4 step applied to an underlying continuous-time ODE. For some `dysts` workflows, cached trajectories can instead come from the `dysts` library's native trajectory generator rather than repeated local RK4 stepping.

## Why this is the right statement

### 1. Training uses discrete windows built from repeated `step()` calls

The training loop consumes sequence windows `x_seq = [x_t, x_{t+1}, ..., x_{t+T}]`, not exact symbolic samples of an analytic flow:

- `tools/train.py:503-517` samples `x_seq` for training.
- `skae/data.py:168-200` builds sequence batches by resetting the environment and repeatedly calling `self.step`.
- `skae/data.py:669-690` defines `generate_sequence_window`, which explicitly constructs `[x_t, x_{t+1}, ..., x_{t+T}]` by repeated stepping.

So the operative object in the code is a discrete-time map produced by the simulator.

### 2. Built-in environments implement one-step numerical integration

The core numerical integrator is:

- `skae/data.py:604-630` `integrate_rk4(...)`

This function returns

```python
x + (dt / 6.0) * (k1 + 2.0 * k2 + 2.0 * k3 + k4)
```

which is a numerical approximation to the time-`dt` flow map, not the exact flow itself.

Representative environments call that RK4 step directly:

- `skae/data.py:726-733` `Pendulum.step`
- `skae/data.py:764-771` `Duffing.step`
- `skae/data.py:808-815` `LotkaVolterra.step`
- `skae/data.py:900-908` `KuramotoOscillators.step`
- `skae/data.py:987-996` `ContinuousHopfield.step`
- `skae/data.py:1109-1120` `CompetitiveLotkaVolterra.step`
- `skae/data.py:1165-1173` `Lorenz63.step`
- `skae/data.py:1209-1216` `Parabolic.step`
- `skae/data.py:1324-1358` `LyapunovMultiAttractor.step`
- `skae/data.py:1526-1538` `MultiWellTransition.step`
- `skae/data.py:1671-1676` `BlendedLinearSystem.step`

So for these environments, the literal semantics are:

```tex
x_{t+1} \approx \Phi_{\Delta t}(x_t),
```

with the approximation implemented by RK4.

### 3. `dysts` environments have two distinct code paths

For `dysts` systems, the ordinary `step()` path is still RK4 over the system RHS:

- `skae/benchmarks/dysts_adapter.py:287-294` defines `_rk4_numpy`
- `skae/benchmarks/dysts_adapter.py:318-347` defines `step(...)`

So without native caching, the same discrete-map interpretation applies:

```tex
x_{t+1} = F_{\Delta t}(x_t)
```

with `F_{\Delta t}` implemented as one RK4 step over `rhs`.

However, when native cached trajectories are enabled, trajectories can come from the `dysts` library's own trajectory generator:

- `skae/data.py:452-525` builds the cache
- `skae/data.py:488-493` calls `self.env.make_trajectory_native(...)`
- `skae/benchmarks/dysts_adapter.py:387-418` defines `make_trajectory_native(...)`
- `skae/benchmarks/dysts_adapter.py:408-413` calls `self.system.make_trajectory(...)`

That path is not “repeated local RK4 stepping in our code”; it delegates trajectory generation to `dysts`.

## Bottom line

The strongest code-faithful wording is:

> We train on discrete-time trajectories generated by a simulator with step size `Δt`. For most built-in environments, the simulator is a one-step RK4 discretization of an underlying continuous-time ODE; for some `dysts` cached trajectories, samples may instead come from the library's native trajectory generator.

That wording is directly supported by the code references above and is more precise than the idealized statement `x_t = x(tΔt)`.
